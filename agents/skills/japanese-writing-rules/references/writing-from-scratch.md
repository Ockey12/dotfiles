# 0から日本語文を書くときの構成

`SKILL.md`の選択条件に該当する文章を0から作成するとき、次の手順で構成する。

## 作成手順

### 読者の判断を決める

文章を書く前に、読者、読者が知りたいこと、読後に判断または実行できるべきことを明らかにする。文章は、筆者が説明しやすい順ではなく、読者が判断する単位で分ける。

1つの節では1つの問いまたは判断だけを扱い、複数の判断が必要なら節を分割する。1つの段落と1つの箇条書きの項目では1つの主張だけを扱い、条件、使い方、例など、役割の異なる内容を無理にまとめない。1つの項目に2つの判断が入ったら、項目を分ける。

受け入れテストなどのチェックリストでは、1つの項目に1つの確認内容だけを書く。確認内容を「〜し、〜で、〜も」とつなげると、一部だけ満たした場合に項目をチェックできない。

悪い例:

```markdown
- [ ] 画像を縦横比を保ったまま中央に表示し、背景は黒
- [ ] iOS 26以降は背景のないバーで表示する。iOS 26未満は不透明なバーで表示する。iOS 17でも表示が崩れない。
```

良い例:

```markdown
- [ ] 画像を、縦横比を保ったまま中央に表示する
- [ ] 背景が黒
- [ ] iOS 26以降は背景のないバーで表示する
- [ ] iOS 26未満は不透明なバーで表示する
- [ ] iOS 17で表示が崩れない
```

### 主語と目的語を明示する

日本語の文章では主語を省略しがちだが、誰が読んでも理解できるように明示する。

目的語も、何を操作するのかが分かる語にする。番号や「この時点」のような指示語だけで対象を指さず、番号が何を数えているか、どの時点を指すかを書く。

悪い例:
- `Profile`ターゲットに`Analytics`を追加する
- 削除は30で行う
- この時点では画面表示のイベントだけを移す

良い例:
- `Profile`ターゲットに`Analytics`への依存を追加する
- 削除はステップ30で行う
- このブランチでは画面表示のイベントだけを移す

### 語彙

「1日溶かした」のような、本来の意味ではない表現を避けて、「1日かけた」のように適切な表現をする。

無理やり漢字2文字にしない。コーディングを「簿記」と言ったり、コードの処理の順番を「簿記」と言ったりしない。文字数が多くなるとしても、一般的に使われる語彙を使う。

### 説明は述語のある文で書く

説明する文は、述語のある文で書く。体言止めや、「コードのみ」「Storyboardなし」のような名詞の羅列で済ませると、何をするのか、何をしないのかを読者が補う必要がある。

悪い例:
- `Profile`ターゲットに`Analytics`と`Model`への依存を追加
- 計測イベントの送信。画面表示と閉じるイベントだけ。

良い例:
- `Profile`ターゲットに`Analytics`と`Model`への依存を追加する
- 計測イベントを送信する。このブランチでは、画面表示と閉じるイベントだけを送信する。

テストケースを「〜こと、〜こと」と1文に並べず、箇条書きの項目に分けて、各項目を述語で終える。

悪い例:

```markdown
テスト: 初期化でユーザーを持つこと、表示時に画面表示イベントを送ること、閉じるときにルーターを呼ぶこと
```

良い例:

```markdown
#### テスト

- 初期化でユーザーを持つ
- 表示時に画面表示イベントを送る
- 閉じるときにルーターを呼ぶ
```

チェックリストの項目のうち、確認する状態だけを示す短い項目は、「背景が黒」のように述語を省いてよい。

### 情報の補足

後から`()`で補足するより、文中で情報を示す構造を優先する。

悪い例: 画面サイズが変わった場合(回転)に、画像の拡大倍率を1にする
推奨する例: 回転で画面サイズが変わった場合に、画像の拡大倍率を1にする

括弧に入れてよいのは、直前の語と同じものを別の形で示す情報だけである。直前の語について何かを述べる情報は、動詞を含まない短い語句でも括弧に入れない。

- 括弧に入れてよい情報: 日本語の語に対応する識別子、別名、範囲の言い換え、具体例、「処理」のような総称が含む内容の列挙
- 括弧に入れない情報: 動作、仕様、説明、理由、文

括弧に入れてよい例:
- ナビゲーションバーにタイトル(`numberingTitle`)を置く
- 購入後の処理(通知の設定、購入イベントの送信、キャッシュの削除)は既存の経路と共通にする

括弧に入れない情報は、直前の語を修飾する語句、別の文、または子項目の文にする。

悪い例:

```markdown
- View: `ProfileViewController`(UIKit、コードのみ、Storyboardなし)
- `scrollEdgeAppearance`に`UINavigationBarAppearance()`(標準の外観)を入れる
- キャッシュを更新する(`Episode(with:)`で型を変換する。`.ticket`は`.ticketCoin`に対応させる)
```

良い例:

```markdown
- View: `ProfileViewController`
  - UIKitを使い、Swiftのコードだけで実装し、Storyboardを使わない
- `scrollEdgeAppearance`に標準の外観である`UINavigationBarAppearance()`を入れる
- キャッシュを更新する。`Episode(with:)`で型を変換し、`.ticket`を`.ticketCoin`に対応させる。
```

括弧と同じく、文の主題とは別の事実を、名詞を修飾する語句に詰め込まない。別の事実は別の文にする。

悪い例: 既存の画面を開く処理を、閉じられる新しい画面を開く処理に置き換える。
推奨する例: 既存の画面を開く処理を、新しい画面を開く処理に置き換える。新しい画面は左上のボタンから閉じられる。

### 判断に理由を添える

変更しない、移行しない、残すなどの判断には、理由を同じ項目に書く。読者は理由から、前提が変わったときに判断を見直せる。判断の根拠を他のチームに確認した場合は、確認した相手も書く。

悪い例:
- 既存の`PurchaseType`は変えない

良い例:
- 既存の`PurchaseType`は影響範囲が広いため、変えない

### 文の繋がり

複数の文章に繋がりがある場合は、接続詞や「これは」「このように」を使って、繋がりを表す。

### まとまりには見出しを付ける

節の中で役割の異なる内容のまとまりを、「目的:」「受け入れテスト:」のような、まとまりの役割を示すラベルの段落で導入しない。まとまりには見出しを付け、見出しのレベルは属する節の1つ下にする。見出しがあれば、読者は見出しの一覧から目的の内容を探せる。

どの見出しにも属さない段落を、節の間に置かない。そのような段落には、役割を示す見出しを付ける。

悪い例:

```markdown
### 1. プロフィール画面

目的: プロフィール画面を新しい実装に置き換える。

受け入れテスト:

- [ ] プロフィール画面を開ける
```

良い例:

```markdown
### 1. プロフィール画面

#### 目的

プロフィール画面を新しい実装に置き換える。

#### 受け入れテスト

- [ ] プロフィール画面を開ける
```

次の2つの場合は、ラベルのままでよい。

- 「悪い例:」「注:」のように、直後の例や段落だけを導入する短い見出し語
- 箇条書きの項目で、「View: `ProfileViewController`」のように対象の名前などの短い値を示す「ラベル: 値」の形

### 同列の見出しを同じ軸で揃える

同じ階層の見出しは、対象、種類、段階、判断など、1つの分類軸で揃える。対象別の見出しに処理順の見出しを混ぜるなど、異なる軸を同列に置かない。

見出しには、読者が目次や検索で探す具体的な概念名を使う。「変換」「関係」「その他」のように、対象や目的が分からない名前を単独で使わない。

### 箇条書きの階層で構造を示す

箇条書きでは、項目の親子関係で内容の構造を示す。読者は親項目だけを拾い読みして全体を把握し、必要な対象の子項目だけを読める。

- 親項目には、対象とそれについての1つの主張だけを書く。補足、理由、詳細は子項目に書く。
- 同じ対象についての項目が複数あれば、対象を表す名詞だけの親項目の下にまとめる
- 条件によって内容が変わる場合は、条件ごとに並列の項目にする。1つの項目に複数の条件を書いて、一方の条件の詳細だけを子項目にしない。
- 型のプロパティ、enumのcase、追加するAPIリクエストのように、構造を構成する要素は子項目に1つずつ書く。親項目の文では「リクエストを2つ追加する」のように、数と種類だけを示す。
- 名前と値の対応は、括弧ではなく「名前: 値」の形の子項目にする

同じ操作の対象を並べるだけの場合は、文中に「、」で列挙してよい。たとえば「`Comic`、`Episode`、`Tag`を`Equatable`に準拠させる」は、子項目に分けなくてよい。

悪い例:

```markdown
- Reducer: `ProfileReducer`(`State`に`User`と投稿の配列を持ち、`Action`は`view`と`delegate`に分ける)
  - `view`アクションは`onAppear`(画面表示イベントを送る)と`onTappedCloseButton`(閉じるイベントを送る)の2つ
- View: `ProfileViewController`。標準の`UINavigationController`でpresentし、閉じるボタンを置く。投稿の一覧は`UICollectionView`で表示する
  - iOS 26未満は不透明なバーにする。iOS 26以降は背景を付けない
    - iOS 26未満では、`scrollEdgeAppearance`に標準の外観を入れる
- APIClient: `ProfileRequest`(GET `/api/v1/users/{id}`)と`FollowRequest`(POST `/api/v1/users/{id}/follow`)を追加する
- Client: `ProfileAnalyticsClient`(`sendImpression`は`screen_profile`、`sendClose`は`close_profile`を送る)
```

良い例:

```markdown
- Reducer: `ProfileReducer`
  - State
    - `User`
    - 投稿の配列
  - Action
    - `view`
      - `onAppear`で画面表示イベントを送る
      - `onTappedCloseButton`で閉じるイベントを送る
    - `delegate`はこのブランチでは実装しない
- View: `ProfileViewController`
  - ナビゲーション
    - 標準の`UINavigationController`でpresentし、閉じるボタンを置く
    - iOS 26未満は不透明なバーにする。`scrollEdgeAppearance`に標準の外観を入れる。
    - iOS 26以降は背景を付けない
  - 投稿の一覧
    - `UICollectionView`で表示する
- APIClient
  - プロフィール画面用のリクエストを2つ追加する
    - `ProfileRequest`(GET `/api/v1/users/{id}`)
    - `FollowRequest`(POST `/api/v1/users/{id}/follow`)
- Client: `ProfileAnalyticsClient`
  - イベント
    - `sendImpression`: `screen_profile`
    - `sendClose`: `close_profile`
```

### 結論を先に書く

節や段落では、結論を最初の1文に書き、理由や背景をその後に書く。理由から書き始めると、読者は最後まで読むまで何を判断すればよいか分からない。

悪い例:

```markdown
開発用アプリは社内に配布し、このブランチのビルドでは新しい画面を開く。テスターは本番アプリも端末に入れているため、開発用アプリの中で画面を切り替える必要はない。
```

良い例:

```markdown
#### 考慮しなくて良いこと

開発用アプリから古い画面に切り替えられないことは、気にしなくて良い。

開発用アプリは社内に配布し、このブランチのビルドでは新しい画面を開く。テスターは本番アプリも端末に入れているため、開発用アプリの中で画面を切り替える必要はない。
```

### 条件を使い方より先に書く

概念や方法を説明する節は、該当する項目を次の順序で書く。

1. 何を扱うか
2. どのような場合に必要か
3. どのような場合には使わないか
4. 具体的にどう使うか
5. 判断理由を代表する例
6. 原則から外れる例外

すべての項目を機械的に設けず、読者の判断に必要なものだけを書く。条件を例より先に示し、例だけから適用条件を推測させない。

### 概要と詳細の役割を分ける

概要、目次、分類一覧は、論点と参照先を示す索引にする。詳細な結論、理由、手順は、それを扱う節だけに定義する。他の節で同じルールが必要な場合は、正本となる節を参照する。

同じルールを複数の節で言い換えて繰り返さない。再掲は、正本の定義をレビュー項目として短く確認する場合だけにする。

### 例で判断理由を伝える

例は、構文や表面的な形だけでなく、そのルールが必要になる理由を代表するものにする。短くても特殊な例や、別の判断でも成立する例を標準例にしない。

例の中だけに新しい条件を置かない。省略した処理が例の意図を左右する場合は、コメントや短い説明で補う。例から本来意図しない一般則を読み取れる場合は、説明を追加するだけでなく、より代表的な例へ置き換える。

### 原則の後に例外を書く

最初に通常の判断を示し、その後に例外の条件と理由を書く。例外を先に示したり、条件を示さず併記したりして、原則と同じ重みを持たせない。

## レビュー項目

- 読者と、読後に可能になる判断または行動が明確か
- 1つの段落、箇条書きの項目、チェックリストの項目が、複数の判断や確認内容を同時に扱っていないか
- 番号や指示語だけで対象を指していないか
- 説明が体言止めや名詞の羅列ではなく、述語のある文になっているか
- 括弧に、直前の語について述べる説明や文を入れていないか
- 変更しない、残すなどの判断に理由が添えられているか
- 段落や箇条書きのまとまりを、ラベルの段落ではなく見出しで導入しているか
- 同じ階層の見出しが1つの分類軸で揃っているか
- 見出しだけで各節の対象を特定できるか
- 箇条書きの親項目に対象と1つの主張だけを書き、詳細を子項目に分けているか
- 条件ごとに異なる内容を、条件ごとの並列の項目に分けているか
- 結論が節や段落の最初の1文にあるか
- 各節が必要になる条件を、使い方や例より先に説明しているか
- 概要が詳細を再掲せず、正本となる節へ案内しているか
- 1つのルールが1箇所だけに定義されているか
- 例が判断理由を代表し、意図しない一般化を招かないか
- 例外が原則の後に、適用条件とともに置かれているか
